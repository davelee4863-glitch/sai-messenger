## Single writer, backup and recovery

Every application mode uses the same exclusive writer lock. Hard links and symlinks are rejected. Staging never automatically removes a stale lock. Controlled normal shutdown releases it. If a same-host writer died, stop the service first, prove no writer remains, then use `node mvp/unlock-writer.mjs --offline --db <isolated-file>`. PID reuse, ambiguous/cross-host identity and a live PID are rejected. Loopback local mode may reclaim only a same-host dead local-mode writer under an exclusive recovery guard, preserving the existing local crash regression behavior; it cannot reclaim a staging writer. A crashed recovery guard fails closed.

Across containers/hosts, do not fabricate PID evidence or delete locks. Stop all replicas using the provider control plane, retain the original DB + WAL + SHM and old locks privately, produce a native backup, restore to a **new path**, then start the one reviewed writer on that path. Provider control-plane recovery is NOT_RUN. Restrict volume write permissions to the one application/operator: standalone provisioning/migration/restore tools are trusted offline maintenance, not a second application writer.

`node mvp/backup.mjs --db <existing-V2-file> --output <new-private-snapshot>` uses a read-only SQLite connection and native online backup, including committed WAL. It may run alongside the one writer. No overwrite. `node mvp/restore.mjs --backup <standalone-V2-snapshot> --output <new-V2-file>` validates exact schema, integrity and foreign keys, refuses live/locked/nonempty-WAL sources, creates a new file and revokes restored sessions. Never manually copy just the main file of a live database. Verify message IDs, promises, RSVP and history before switching DB paths.

`node mvp/migrate-v1.mjs --source <isolated-V1-copy> --output <new-V2-file>` validates a complete V1 schema, snapshots committed WAL and migrates only the new copy. Original bytes/data are preserved. V1 join timestamps cannot establish order within one millisecond, so migrated users see only future records; previous records remain archived without an implicit sharing grant. Old sessions are revoked. No automatic or reverse migration.

For rollback: stop one writer, snapshot the current DB, select the previous independently validated **V2-compatible** code/image and compatible snapshot, restore to a new path, revoke sessions, run smoke/recovery tests and manually switch the approved version. PR4 V1 code cannot open V2; returning to V1 needs its preserved original V1 archive and sacrifices later V2 activity unless a separately reviewed migration exists. Keep those branches/images distinct. Real hosted rollback is NOT_RUN; tested local recovery does not certify provider snapshots.
